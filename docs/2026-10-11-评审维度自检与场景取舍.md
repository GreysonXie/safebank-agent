# SafeBank：评审维度自检与场景取舍

日期：2026-10-11。代码审查基线：608ff2e，v0.7 Python LangGraph + Java/MyBatis + MySQL 候选。本文是代码与既有证据审查，没有新跑完整测试、没有调用 DeepSeek、没有实现新增场景。评分权重来自用户提供的评审标准；场景及权限要求以用户提供的[赛题分析](D:/2.临时消息文件/研一/深金赛/赛题分析.md)为工作依据，正式提交前须与组委会最终附件核对。

官网索引的六场景及至少三个方向已核对，动态详情与完整评分未独立提取；来源和限制见[场景来源核对](2026-10-11-评审场景来源核对.md)。

## 1. 判断

现阶段已有相对扎实的执行安全基础，但“自然语言办理业务”的完整度弱于后端功能完整度。最大的缺口不是少一个菜单，而是当前 Python 对话只读，转账和撤销仍需客户进入业务页操作；既有跨场景联动也主要依靠预设流程和表单。应先把三个已有场景做成完整 Agent 闭环，再升级跨场景联动。暂不新增理财或卡片模块。

不给出虚构的自评分。历史版本的交付率、合成后端测试、当前版本少量真实模型问答不能混合成“总任务完成率”，也不能据此预测比赛分数。

| 评审维度 | 当前可支持的优势 | 主要缺口 | 优先级 |
|---|---|---|---|
| 任务完成率 40% | 已有转账/计划、账单及代扣后端；账单比较与连续追问有真实模型样本；已有固定联合任务服务 | 当前对话没有收款人查询、转账/撤销预览工具；操作入口与对话脱节；固定流程不能证明可从自然语言生成任务 DAG | 最高 |
| 安全合规性 30% | Java 决定身份/权限/金额和授权；短期限定 scope；回执归属与哈希；日累计分级；状态未知不自动重发 | 确认不等于防骗；缺少专门诱导转账处理机制和当前版本完整攻击矩阵；模拟 OTP 不是真实 MFA | 高 |
| 创新性及交互体验 30% | 对话与业务分区、依据展示、历史整组折叠；可恢复图和费用回执 | 重复摘要、无关补充、格式拒绝仍影响体验；用户改口未完整延伸到待确认动作/计划；框架本身不是创新 | 高 |

## 2. 代码和证据：不能混淆的边界

1. `ContextAgentCoordinator` 检测网关后直接调用 `GatewayCoordinator`，不是 Python 不支持时自动转回旧 Java 写操作 Agent。当前 Java `AgentCapabilityService.SCOPES` 和 Python `prompts.PLAN` 仅允许 statement、statement_compare、recurring_analysis、account_query、mandate_receipt。旧 Java 支持写预览不等于当前 Python 对话已具备它。
2. `WorkflowService.advance` 已有逐项月付授权撤销、按已核验结果生成储蓄计划预览的固定联合流程，且有版本/归属/未知状态约束。应称“已有受限联动”，不能称“完全没有联动”；也不能据此称“自然语言自主生成任意 DAG”。转账到本人储蓄账户不是理财产品申购。
3. `RiskPolicyService.evaluate` 根据动作类型及有效日累计决定确认或强验证，当前没有在该规则内看到诈骗意图分类。拒绝越权工具、阻止未经授权的支付与识别受诱导的合法用户付款是两类问题，需分别展示证据。
4. [24 场景真实验证](2026-10-11-六批二十四场景真实压力验证.md)针对旧提交 2947505：24 题、53 次模型调用、17 次 HTTP200、7 次未交付。HTTP200 中仍有语义问题，不报告为 70.8% 任务成功。后续原题修复样本来自不同版本，不能拼成当前版本全套通过。
5. [最近追问复验](2026-10-11-无效引用反馈修复与追问复验.md)两题同会话正确交付，4 次模型请求，并完成 Java ACK/哈希/版本核对；是首稿通过样本，未真实触发新增引用候选恢复。仍有未问的结构分析和负号展示问题。
6. [页面历史折叠验证](2026-10-11-历史记录整体折叠与回答去重.md)覆盖桌面、手机及用户反馈宽度，但该页面流程使用模拟模型，不能证明真实模型全面稳定。
7. 银行身份、账务、MFA 均为本地合成演示。不宣称真实银行接入、真实金融合规认证或生产可用。当前没有开放任意代码执行，不把这一点写成已实现代码执行沙箱。

## 3. 三个功能先做到什么程度

### 智能转账：优先补对话与受控预览之间的桥梁

目标体验：客户说“给小张转五百”→查询本人可用收款候选→重名时只问必要识别项→Java 生成展示预览→用户核对账户/对象/金额/时间后明确确认→需要时完成模拟强验证→Java 执行→依据原 action_id 回执说明结果。

Python 只能提出有限、结构化的查询/预览请求。身份来自 Java 会话，金额规范化与校验、归属、风险分级、授权、执行仍在 Java。新增预览也会创建数据库记录，必须限制参数、操作数量并做幂等，不能把“预览无资金变化”当成没有副作用。

客户改金额、收款人或日期后，旧预览及旧授权不得继续使用；已受理或 UNKNOWN 的动作先查原单，不能自动改参重发。不能为减少轮次而把多笔资金操作隐含合并授权。

先完成即时转账与既有定时能力。AA 收款、手机号入口等示例不是本阶段必须全部扩展的功能。

### 账单分析：回答具体问题，不把每次查询变成报告

总览、最大支出、退款、跨月变化、用途是否合理各用相关事实回答。没有月份且上下文无法确定时才补问；客户已指定范围时不主动展示完整清单。金额与合计仍由 Java 计算，引用存在不能替代语义一致性检查。

退款入账与既定支出口径、大额候选与欺诈判断、授权存在与实际交易通道都要区别。核验失败保留已经成功的查询结果，说明当前无法可靠作答及可继续的选择，不直接给泛化模板，也不放宽校验换取成功率。

### 代扣管理：从建议安全抵达撤销预览

历史周期消费只产生候选；当前授权列表遵守黄色确认要求。只读查询有效确认快照期间不反复确认，过期/重置/撤销导致失效时提示重新确认，并保留客户刚才所问的服务和范围。

对话理解“视频暂时不用了”后先说明已有依据、缺失背景与撤销边界，再生成指定服务的待确认预览；不能凭表达推断已获得撤销授权。银行侧撤销不证明商户合同终止、退款或以后绝无收费。

仅确定有效 MONTHLY 授权可形成条件性月付预算估计，季度/未知周期、历史账单支出不冒充每月可节省金额。未知使用频率不得替客户决定“哪个最没用”。

## 4. 安全能力需要补齐的内容

- **诱导转账**：针对“保证金/解冻费/安全账户/别人让代付”等上下文形成专门风险处理；先询问可验证的目的、提示风险，明确高风险情形的暂停/人工核查路径。风险不能只因金额小或用户点击确认就自动消失，模型也不能单独决定降级。规则覆盖范围与误报要在证据中披露。
- **信息套取**：拒绝索要/输出登录密码、支付密码、验证码；敏感输入进入模型前的检测、遮罩和日志治理需单独设计，不能仅靠回答提示词。只处理当前用户允许的对象，合法查询也采用必要范围。
- **注入与越权**：用户请求、商户备注、工具错误消息、旧对话污染分别作为攻击入口。后端白名单/归属/授权校验必须在模型被诱导时仍成立。已有合成阻断证据可以复用，但要区分旧 Java 路由与当前 LangGraph 路由。
- **授权与恢复**：覆盖确认后改参、过期回执、重放、跨会话、重复点击、日累计跨阈值、提交后超时、部分成功。资金已完成后不能通过“取消任务”宣称回滚；UNKNOWN 保留并查原单。
- **安全拒绝体验**：不执行之外，还应说明拒绝原因与用户可以采取的下一步，不暴露内部工具名、令牌或安全凭证。

建议按“攻击/预期拒绝或确认/实际工具/授权记录/资金是否变化/客户可见回答”记录证据。安全防御、语义正确性和使用体验分别计量，不能互相替代。

## 5. 新场景取舍：升级跨场景联动

| 候选方向 | 与现有能力的关系 | 新增负担 | 建议 |
|---|---|---|---|
| 跨场景联动 | 已有账单、代扣、储蓄计划和固定 WorkflowService | 补目标理解、受限计划生成、改口/确认/恢复及解释 | 首选，先升级既有固定联动 |
| 卡片管理 | 部分确认、审计基础可复用 | 新卡片数据、状态、业务适配与挂失等强验证 | 联动完成后再评估单一清晰场景 |
| 理财操作 | 权限框架可复用，数据与交易模型不同 | 产品事实、风险适配、申购/赎回状态和解释边界 | 本阶段暂缓 |

这不是比赛方对三个方向的偏好排名，而是基于四人团队与当前代码基础的工程取舍。

建议亮点名称：**可恢复的目标储蓄任务**。示例：“想为旅行留钱，看看哪些订阅可以调整，改动前都让我确认。”Agent 根据账单和已确认授权说明候选，追问客户愿意调整的服务与目标账户/时间，展示分步计划和依据；用户逐项确认，Java 执行。客户临时保留一个服务时重新核算计划并重新确认；某一步状态未知时暂停依赖节点，通过原单恢复，解释已完成和未完成部分。

“撤销月付→立即得到同额现金→转入储蓄”不成立：预计减少未来支出不证明已经省下现金，也不证明可用余额足够。创建储蓄计划仍需当前余额、时间和用户选择的金额校验，不承诺旅行目标必然达成。可以取消未受理的后续步骤，不能自动逆转已完成银行动作。

实现采用有限节点和合法依赖的类型化计划，Java 校验归属、参数和业务规则，LangGraph 负责澄清、计划推进、等待与恢复。先支持一条明确组合任务，不开放任意工具编排，不为亮点再引入多智能体或新框架。

亮点需要实际演示“理解目标→追问关键缺失→展示依据与依赖→客户改口→局部成功/故障→安全恢复”，而不是仅展示更多页面或宣称采用 LangGraph。

## 6. 推进顺序与进入下一阶段的条件

1. 优先实现现有转账、代扣的自然语言查询/预览桥梁，保持确认与执行在 Java；同时补诱导转账/敏感信息处理设计。
2. 精简账单和代扣回答，保证改口/追问对应当前问题；服务失败后提供明确下一步。
3. 将现有固定联合流程升级为上述一条受限目标任务，再考虑独立新增卡片或理财功能。
4. 最终用同一版本的小型固定验收集验证三个场景：每类包括正常办理、缺参数、连续追问/改口、权限或确认阻断、故障恢复。基础任务通过后增加组合任务，不重复全量付费测试去追求某一次漂亮结果。

指标定义：任务完成须满足正确结果或预先定义的必要澄清/拒绝终态、工具和对象正确、权限符合、无重复副作用；正常任务被不必要拒绝计失败。另记录客户轮次、澄清必要性、无关段落、恢复是否重复请求、模型请求数和实际 usage。测试工具可以自动核对数值/状态/调用，语义与交互质量另行核对。

材料同步：现有参赛材料主段落仍保留“待 M3/仅 M2”等历史文字，而末尾已追加 M3 完成记录，容易让审阅者误解。材料首页应给出当前版本、已实现范围及开放风险，再将历史阶段作为证据。第 1、2、5 项继续阶段性维护；PPT/视频和最终发布包按用户要求留到收尾。

本自检建议中的预览接入、反诱导完善与目标任务升级都属于下一阶段工作，不能在当前作品介绍中宣称已实现。
