# SafeBank Agent 框架官方能力核查

核查日期：2026-10-10（北京时间）。范围：官方文档、固定 tag 源码、发布记录；本次没有安装依赖、构建适配、启动服务、读取密钥或调用 DeepSeek。下文“核实”表示文档或源码支持；“判断”表示针对本项目的设计推断；“待验证”表示不能由资料替代运行验证。动态文档可能随发布更新，版本关键判断优先使用固定 tag。

## 结论与推荐边界

**判断：当前团队适合 Java 模块化单体、单协调 Agent、受控持久化任务图。模型接入优先评估 Spring AI 1.1.8；图引擎单独评估 LangGraph4j core，暂不直接引入最新 Spring AI integration。** 用户问题由模型产生有类型的任务提案，后端校验工具白名单、依赖、参数来源和计划版本，再执行图。银行授权、账务、幂等、回执服务继续是独立的确定性业务边界。

Spring AI 是模型/工具/消息抽象，不能仅靠接入它宣称获得持久化任务图。LangGraph 官方也将模型/工具组件与图运行时区分，并允许在图中混合确定性和模型节点。[LangGraph 官方定位](https://docs.langchain.com/oss/python/langgraph/overview)

可选路线：

| 路线 | 对本项目的适用判断 | 关键条件 |
|---|---|---|
| Spring AI 1.1.8 + 受控图执行接口，LangGraph4j core 作为候选实现 | 首选；沿用 Boot/MyBatis，模型循环与任务执行分别整理 | 禁用隐式工具循环和默认重试；验证 Jackson/序列化/恢复兼容性 |
| LangChain4j + LangGraph4j | 合理备选；Java 工具和图有官方集成示例，DeepSeek reasoning 字段可配置 | 固定匹配版本；核查 beta 传递依赖；不能把通用 AI Services 自动循环直接当银行执行器 |
| Python LangGraph + Java 银行后端 | 能力较完整的备选，长期图编排/研究资源较丰富 | 增加 Python 主力、第二服务部署、身份/回调/幂等接口和跨服务故障处理 |
| AgentScope Java | 有 Agent、权限、运行控制与状态存储能力，作为后续备选 | 当前大版本迁移较明显；团队必须学习新的 Reactor/runtime/权限语义；不能替代银行授权 |

上述排序是团队技能、现有资产和迁移风险的判断，非官方性能排名。没有实测证明某框架会让当前自由回答通过率自动提高。

## 版本兼容性：不能直接选网页上的 latest

1. **核实：Spring AI 1.1.8 是已发布稳定版本，其发布记录升级到 Spring Boot 3.5.15；1.1 开发线文档说明支持 Boot 3.4.x/3.5.x。** 因而它是现有 Boot 3.5.6 的同代候选；不等于已经验证 3.5.6 的每项传递依赖。Spring AI 2.0.0 发布记录升级到 Boot 4.1.0，不能盲换 2.x starter。[固定发布记录](https://github.com/spring-projects/spring-ai/releases/tag/v1.1.8)、[1.1 兼容范围](https://docs.spring.io/spring-ai/reference/1.1-SNAPSHOT/getting-started.html)、[2.0 发布记录](https://github.com/spring-projects/spring-ai/releases/tag/v2.0.0)

2. **核实：LangGraph4j v1.9.3 的父 POM 固定 Spring AI 2.0.1、LangChain4j 1.20.2/1.20.2-beta30；v1.8.27 也固定 Spring AI 2.0.0。** “选择 LTS 1.8 就能直接配 Spring AI 1.1”并不成立。许可证为 MIT，Java 基线 17。[v1.9.3 POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/v1.9.3/pom.xml)、[v1.8.27 POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/v1.8.27/pom.xml)

3. **核实：v1.8.27 core POM 未声明 Spring AI/LangChain4j，声明 async-generator 4.3.1，Jackson 2.21.1 和 Gson 2.10.1 均为 provided。** v1.9.3 core 同样无模型框架依赖，async-generator 为 5.0.0。判断：只用 core、图状态存项目自有 DTO、节点调用 Spring AI 1.1.x，是可评估的薄桥接路线。待验证：项目 Boot 管理的 Jackson 2.19.x 是否覆盖 core 所用 API、序列化能否稳定往返。provided 不意味着所有版本都兼容，不能强行覆盖后宣布成功。[v1.8.27 core POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/v1.8.27/langgraph4j-core/pom.xml)、[v1.9.3 core POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/v1.9.3/langgraph4j-core/pom.xml)

4. **核实：LangChain4j 当前 Spring 集成文档支持 Java 17、Boot 3.5+ 对应 `-spring-boot-starter`，Boot 4 对应另一组 starter。** 发布同时存在 stable 与 beta 模块；截至本次核查发布页已有 1.22.0，但 LangGraph4j 1.9.3 固定的是 1.20.2，不能两边独立升级。[Spring 集成范围](https://docs.langchain4j.dev/tutorials/spring-boot-integration/)、[发布记录](https://github.com/langchain4j/langchain4j/releases)

5. **核实：LangChain4j 1.20.2 OpenAI 模块自身为 stable 版本，但传递依赖 reactive-streaming 1.20.2-beta30；LangGraph4j 1.9.3 的 LangChain4j integration 编译依赖 skills beta30。** “用 stable 模型包，整条依赖链没有 beta”也不成立。可仅用 provider-neutral core + 低层 ChatModel 降低集成面，但仍需查 dependency tree。LangChain4j 仓库声明 Apache-2.0。[模型 POM](https://raw.githubusercontent.com/langchain4j/langchain4j/1.20.2/langchain4j-open-ai/pom.xml)、[图集成 POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/v1.9.3/langchain4j/langchain4j-core/pom.xml)、[许可证](https://github.com/langchain4j/langchain4j)

## Spring AI 1.1.8 的可用能力与限制

### 模型、工具、预算

**核实：有 DeepSeek 原生 ChatModel。** v1.1.8 的 `DeepSeekChatModel` 解析工具请求、usage 和 reasoning 文本；`internalCall` 将 HTTP 调用放入 RetryTemplate，再按工具条件递归执行并继续请求。[固定源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/models/spring-ai-deepseek/src/main/java/org/springframework/ai/deepseek/DeepSeekChatModel.java)

**核实：1.1 工具 API 支持 `internalToolExecutionEnabled(false)`；调用方读取 tool calls 后决定是否交 ToolCallingManager。** 这适合 SafeBank：按当前意图提供工具子集，校验参数、预算、用户身份后才执行。工具异常默认可能转为模型可见错误；业务中止应明确映射，避免模型反复尝试。该 API 在 2.x 已变化，不能混用教程。[1.1 工具文档](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html)

**核实：固定 v1.1.8 RetryUtils 默认 `maxAttempts(10)`。** 对用户“不要花费过多”的约束，迁移时首先设单次尝试，所有外层修复/审核也统一计入预算。[RetryUtils 源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/spring-ai-retry/src/main/java/org/springframework/ai/retry/RetryUtils.java)

**核实：DeepSeekApi 接受 RestClient.Builder/WebClient.Builder，非流请求由 RestClient 发送。** 判断：现有硬预算应在 HTTP 发送前预留，非流 transport interceptor/自定义客户端是候选接缝；如果未来流式则另需 WebClient filter。只在 ChatClient advisor 统计一次逻辑调用，不能覆盖内部重试与工具后续发送；Micrometer usage 是观察数据而非硬额度锁。[DeepSeekApi 固定源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/models/spring-ai-deepseek/src/main/java/org/springframework/ai/deepseek/api/DeepSeekApi.java)

### 类型输出与记忆

**核实：BeanOutputConverter 生成 schema 提示并把文本读为对象；默认 ObjectMapper 忽略未知字段。** 因此模型任务计划仍需要额外 schema/Bean Validation/白名单/语义校验，不能把“成功转换 DTO”当作受控 DAG 已合法。Spring AI 授权仍由应用承担；许可证 Apache-2.0。[固定 converter 源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/spring-ai-model/src/main/java/org/springframework/ai/converter/BeanOutputConverter.java)

**核实：ChatMemory 与 repository 能管理会话消息；1.1 文档明确工具循环中间消息目前不自动存入 memory，需 user-controlled 工具执行。** 判断：保留项目已有业务槽位/银行事实/参数来源，它们与聊天消息用途不同；不应用通用滑动窗口覆盖银行证明。图 checkpoint 也不能取代业务数据库。[1.1 ChatMemory](https://docs.spring.io/spring-ai/reference/1.1/api/chat-memory.html)

### 观测

**核实：Spring AI 提供模型、工具、advisor 的 Micrometer observations/token metrics，默认不导出 prompt/completion/工具内容。** DeepSeek 是否上报齐全仍应按固定源码与离线响应测试核实；当前通用观测文档提供者名单与 DeepSeek 源码有不完全一致之处。判断：为每轮关联 turnId、runId、nodeId、bankActionId、预算预留记录和 provider response id；只保留必要脱敏信息。[1.1 observability](https://docs.spring.io/spring-ai/reference/1.1/observability/index.html)

## LangGraph4j 的任务图、暂停和恢复

**核实：core 支持 StateGraph、条件边、CompileConfig 的 checkpointSaver/recursionLimit、执行前后 interrupt，以及动态 InterruptibleAction；恢复需要 checkpointer 与稳定 thread 标识。** 1.9 文档还描述 GraphInterruptException、GraphInput.resume。判断：有限节点集合的受控业务任务图可落在这里，但图编译的结构检查不包含银行权限和业务正确性。[core 能力文档](https://langgraph4j.github.io/langgraph4j/1.9/core/core-library/)

**核实：有内存、文件及多种数据库 checkpoint saver；1.9 的恢复、stream engine、serializer、checkpoint release 语义有变化，完成运行默认释放 active thread，中断/异常则保留。** 不能把 1.9 功能细节直接当作 1.8.27 行为保证。持久化 serializer 必须与旧 checkpoint 格式兼容，不能随升级切换 binary/JSON。[1.9 迁移说明](https://langgraph4j.github.io/langgraph4j/1.9/whats-new-v1.9/)、[持久化示例](https://langgraph4j.github.io/langgraph4j/1.9/how-tos/persistence/)

**判断：必须另验四项恢复契约。** 进程重启后等待确认节点可恢复；改口后旧 plan version 的 resume 被拒；发送银行请求后节点崩溃只能核验原 action 的 UNKNOWN/回执；重复恢复不新建 action。checkpoint 保存了图位置，不与银行提交自动组成同一个原子事务，也不保证外部调用 exactly-once。

**核实：项目说明 1.8.x 为 LTS、1.9 为准备 2.0 的功能线且包含实验特性；它是受 LangGraph 启发的独立 Java 项目，非 Python LangGraph 本体。** 判断：优先小范围验证 core/checkpointer，不把 skills/subagent/Studio 等整套引入银行主链路。[官方仓库定位与版本线](https://github.com/langgraph4j/langgraph4j)

## LangChain4j + LangGraph4j 的额外价值与注意点

**核实：OpenAI-compatible ChatModel 支持 DeepSeek base URL，并可控制 returnThinking/sendThinking；structured outputs 可选 schema 或提示方式，后者官方明确可靠性较弱。** 实际 DeepSeek 是否支持该 schema 功能仍由供应商决定，OpenAI schema 能力不能自动移植。[OpenAI-compatible 接入](https://docs.langchain4j.dev/integrations/language-models/open-ai/)、[structured outputs](https://docs.langchain4j.dev/tutorials/structured-outputs/)

**核实：固定 1.20.2 OpenAiChatModel 默认 maxRetries=2，retry 在 doChat 内；ChatModel onRequest/onResponse 位于 doChat 外。** 所以 listener 调用次数不必等于实际 HTTP 尝试次数。判断：设 maxRetries=0，并通过 transport/单次 model 包装保持预算；不能依赖 onRequest 硬计数覆盖重试。异步 ChatModel 方法标记 Experimental。[模型固定源码](https://raw.githubusercontent.com/langchain4j/langchain4j/1.20.2/langchain4j-open-ai/src/main/java/dev/langchain4j/model/openai/OpenAiChatModel.java)、[ChatModel 固定源码](https://raw.githubusercontent.com/langchain4j/langchain4j/1.20.2/langchain4j-core/src/main/java/dev/langchain4j/model/chat/ChatModel.java)

**核实：ChatMemoryStore 能持久化消息，但被窗口淘汰的消息也会从 store 删除；ChatMemory 不等于完整 UI 历史。** 项目应保留独立审计/业务证据，不将用户真实意图来源交给模型总结覆盖。[ChatMemory 官方说明](https://docs.langchain4j.dev/tutorials/chat-memory/)

**核实：模型 listeners 与 Micrometer metrics/observations 可用于观测；低层工具调用和 AI Services 高层工具循环均有 API。** 判断：若采用此路线，优先低层 ChatModel + 项目 ToolGateway；银行写入串行受控，不能默认开启通用并发工具执行。[observability](https://docs.langchain4j.dev/tutorials/observability/)、[tools](https://docs.langchain4j.dev/tutorials/tools/)

## Python LangGraph + Java 银行后端

**核实：固定 LangGraph 1.2.12 包声明 Python>=3.10、MIT、Production/Stable；LangGraph 能独立于完整 LangChain 使用。** 判断：这条路线是长期图能力较强的选项，但对四人且仅一位 Java 主力的团队，双进程、两套依赖和测试、服务鉴权/网络超时/恢复回调成本实际存在。[固定 pyproject](https://raw.githubusercontent.com/langchain-ai/langgraph/1.2.12/libs/langgraph/pyproject.toml)

**核实：checkpointers 持久化 thread 图状态，stores 保存跨 thread 应用数据；InMemorySaver 重启会丢失，生产应换持久化 saver。** 图状态只保存 actionId/plan version/授权状态引用；Java 后端仍负责事实和资金状态来源。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

**核实：interrupt 保存状态后暂停，用同一 thread 的 Command(resume=...) 恢复；恢复会从中断节点开头重跑，中断前副作用必须幂等。** 判断：`resume=true` 只是图输入，不能当银行授权凭证；授权由 Java 服务核对用户、参数摘要、版本和有效期。[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

**核实：有 sync/async/exit 持久化模式；重放 checkpoint 后的节点会重新执行包括模型/API请求，DeltaChannel 在1.2线仍标 beta。** 判断：银行关键图优先 sync；重放必须经已有 action 状态/幂等核对，并继续计入模型预算。[Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

**核实：有 ChatDeepSeek 与工具绑定、structured-output 接口、可配置 max_retries；官方示例展示重试设置。** 判断：关闭 SDK 隐式 retry，与图级 RetryPolicy 合并为一个发送前额度网关；LangSmith 可观测不等于额度熔断。运行库 MIT 与托管 tracing/deployment 的产品条款应分别核查，本项目不必为 OSS 图运行强制购买托管服务。[ChatDeepSeek reference](https://reference.langchain.com/python/langchain-deepseek/chat_models/ChatDeepSeek)、[structured-output reference](https://reference.langchain.com/python/langchain-deepseek/chat_models/ChatDeepSeek/with_structured_output)、[LangGraph 产品职责](https://docs.langchain.com/oss/python/langgraph/overview)

## DeepSeek 供应商约束：框架不能替代核对

**核实：当前官方 Tool Calls 文档把 strict schema 声明为 Beta，要求 `/beta` 与 function.strict=true；思考模式不支持 required/指定 tool_choice。** 结构正确仍不证明收款人/金额来自用户明确选择。默认候选应先使用非强制工具、应用侧严格校验，不擅自将 Beta 作为银行正确性保证。[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[中文 API 参数](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

**核实但待运行响应验证：** 2026-10-10 访问旧 `guides/function_calling` 时官方返回首页内容，模型表附注称旧 deepseek-v4-flash 名称仍接受、由V4.1-Flash服务，页面短引：`“their requests are served by the DeepSeek-V4.1-Flash model”`。直接根 URL 本次另一次访问超时，未据此改配置。今后请求保留用户选择，并记录响应 model/日期，不能把别名视为固定权重版本。[本次可访问官方 URL](https://api-docs.deepseek.com/guides/function_calling)

**源码差异：** Spring AI1.1.8 DeepSeek 接收 reasoning_content，但组装下一轮 assistant 时置空该字段；1.20.2 LangChain4j 有 sendThinking 控制。判断：新模型 thinking+tools 多轮兼容性必须用脱敏录制报文/本地 mock 先验证，不能从“支持 DeepSeek”四字推导支持当前所有 reasoning 语义；必要时选择非thinking或另评估兼容适配器。见前述两份固定 ChatModel 源码。

**补充核实：原生 DeepSeek starter 1.1.8 不能通过现成 Options 原样配置本项目现有的 `thinking: {type: disabled}`。** 固定 `DeepSeekChatOptions` 的字段、Builder 与复制逻辑没有 thinking 或通用 extra-body/custom-parameters；`DeepSeekApi.ChatCompletionRequest` 也是无 thinking 字段的固定 record。模型 createRequest 把选项合并到该请求类型，再由 API 将 record 作为 HTTP body 发送。`internalToolExecutionEnabled(false)` 仅关闭框架自动执行工具，完全不是关闭模型思考模式，二者不能混淆。故直接换 starter 会丢失显式非思考字段，不能称其为满足当前请求契约的无修改替代。判断：Spring AI 仍可作上层模型/消息抽象候选，但 provider 层需自定义请求映射/发送适配，或暂保留现有 native provider adapter；其报文与发送前预算契约通过后才迁移。不要通过改 DeepSeek 模型别名或假定供应商默认非思考来绕过该限制。[固定 Options 源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/models/spring-ai-deepseek/src/main/java/org/springframework/ai/deepseek/DeepSeekChatOptions.java)、[固定 API 请求与发送源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/models/spring-ai-deepseek/src/main/java/org/springframework/ai/deepseek/api/DeepSeekApi.java)、[固定模型构造请求源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/models/spring-ai-deepseek/src/main/java/org/springframework/ai/deepseek/DeepSeekChatModel.java)
