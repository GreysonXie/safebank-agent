### 实际核验

1. README 列 Java 17、Spring Boot 3.3.5、JDBC/Flyway、RabbitMQ、Redis、PostgreSQL/pgvector、FastAPI、静态 HTML/CSS/JavaScript。已阅读的源码确实使用 Spring Service、RedisTemplate、Java record 与业务服务分层；完整依赖版本仍以 pom 为准，不把 README 的版本表当作构建验证。
2. 工作流源码存在五个任务类型及串行的下一阶段映射：采集、指标计算、文档索引、公司情报、AI 分析。这证明五阶段流程存在，不能据此说有五个独立自治 Agent，更不是自由规划的银行交易 DAG。源码包含 lease 获取、心跳、运行/成功/失败状态，以及通过 `saveIfOwned` 和 fencing token 限制状态写入。
3. Redis 单飞不是只有文案：租约服务存在 Lua 原子获取、递增 fencing token、TTL、按 owner/token 比较后续租或释放；工作流与分析使用不同命名空间。也存在默认允许的进程内 fallback。**本地 fallback 无法提供跨进程互斥**，应与分布式保证分开表述；本次没有做并发故障测试。
4. 报告快照存在源码：分析服务依据 contextHash 形成数据快照 hash 和缓存键，检查历史报告的 contextHash，获取分析租约后再次检查缓存，响应带 reportId、生成时间、snapshotHash、reportVersion、citations、source、aiGenerated。该文件将实际持久化委托给 reportPersistence；未继续验证存储事务及历史版本一致性。

## 对当前 SafeBank 的结论

上述表格共给出五处具体设计候选。最优先是 FinSight 的审核输入快照/来源版本、现有状态机的任务关联，以及 Azure 样例的业务服务与工具入口分离；Redis、MCP、云 OCR 和新增框架应待真实需要再引入。保留 Spring Boot 3.5、Java 21、MyBatis、H2、自定义 gateway 与状态机，先补比赛要求的服务端权限、累计规则、动作绑定授权和结构化审计。

报告、缓存和任务租约主要解决可追溯性与重复计算，不能替代交易安全。模型生成建议或预览后，资金动作仍由服务端规则与用户逐动作授权控制；UNKNOWN 必须查询原 action_id，不能借重试创建新资金动作。
