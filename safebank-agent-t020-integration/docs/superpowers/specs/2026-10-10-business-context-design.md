# v0.6 第一阶段：业务记忆与澄清设计

状态：用户2026-10-10已批准设计和 Native 执行，v0.6 隔离候选已实现；原 v0.5/8096 保留。当前实现范围、真实问答的部分通过及尚未展开的测试见 `docs/2026-10-10-业务记忆实施验收.md`。实施计划见 `docs/superpowers/plans/2026-10-10-business-context-implementation.md`。

## 目标和边界

用户已同意优先提升业务记忆、澄清、任务承接和回答针对性，并允许少量 DeepSeek 调试。第一阶段让现有账单、转账、代扣、联合储蓄流程在多轮对话中可靠承接：记住讨论对象、只问缺失参数、正确处理改口和暂停、沿用权威回执。保持左侧导航、中间业务、右侧对话和移动端底部对话。

本阶段实现持久化上下文与澄清，不宣称已完成通用 DAG。下一阶段基于这些状态扩展受控节点规划；现有 WorkflowService 的版本、暂停、修改及原动作恢复继续复用。本阶段不加入长期人格记忆、向量库、新 Agent 框架或多模型角色。

替代方案：只追加提示词成本低，但丢失会话后无法恢复，也不能明确区分提案与授权；一次替换全部工作流为通用 DAG 会同时改变安全和执行接口。采用增量业务上下文方案，先稳定多轮理解，再扩展规划。

## 当前实现依据

- AgentService 在 HttpSession 中保存 conversation/answerEvidence，聊天裁剪为最近四轮，证据保留最多四项；不是持久化业务上下文。
- 已有自由回答、GroundedAnswer 事实校验、BusinessAnswerReview 语义审核和按工具生成的兜底说明；保留这些能力，补齐失败时对当前问题的聚焦。
- 所有工具定义随每次生成请求发送；默认每轮请求上限为 12，模型协议 max_tokens 为 2048。本阶段不通过删除安全审核节省费用。
- 代扣查询为黄色确认动作，AgentService 返回确认卡并暂停；后续确认所得数据必须通过服务器读取已完成查询的权威回执，不能靠前端重新提交内容作为事实。
- WorkflowService 已提供有版本的联合任务和修改/取消/恢复；复用其业务服务，不另写银行执行引擎。

## 数据库设计

新增四表，完整草案见 `docs/database/2026-10-10-business-context.sql`。保持现有 20 表；先审设计，再通过独立初始化/迁移实现，仅用于新候选或经过审核的副本，不自动修改8096或真实旧文件库。

| 表 | 职责 | 关键约束 |
| --- | --- | --- |
| agent_conversations | 归属、上下文版本、活动主题、当前提案、状态 | PK id；UNIQUE(id,user_id)；版本≥1；状态显式枚举 |
| agent_context_slots | 月份、对象、候选、参数、缺失项及来源 | 每会话每槽唯一；复合归属外键；写入绑定版本 |
| agent_context_evidence | 可引用的银行事实快照及对象关联 | 每会话每事实唯一；摘要哈希、获取时刻和有效性明确 |
| agent_turn_receipts | 一轮请求的幂等、处理状态、上下文版本和结果 | UNIQUE(conversation_id,user_id,request_id)；保存请求哈希 |

标识 VARCHAR(80)，user_id VARCHAR(40)，金额 BIGINT 整数分；版本 BIGINT；时刻 TIMESTAMP WITH TIME ZONE，使用注入 Clock。模型协议/候选参数 JSON 由强类型 codec 校验，不能直接反序列化为授权实体。DTO 是请求，Entity 是数据库记录，VO 是展示。

槽白名单：primary_month、comparison_month、focused_transaction_id、recipient_candidates、selected_recipient_id、source_account_id、amount_minor、mandate_candidates、selected_mandate_ids、excluded_mandate_ids、first_date、end_date、day_of_month、active_action_id、active_workflow_id、missing_slots。候选数组上限10、代扣选择上限10；同一项不得同时选中和排除。缺失槽只从这些业务参数中选择。

槽来源区分 USER_EXPLICIT、MODEL_PROPOSED、BANK_CONFIRMED；来源标签由服务器按证据生成，模型不能声明 BANK_CONFIRMED。槽附带 source_turn_id、evidence_id 和写入版本；MODEL_PROPOSED 只能表示待核对建议。任何槽、聊天摘要或恢复记录都不是 grant。

证据优先存可重读的银行对象引用；历史账单快照保存规范化结果与哈希，按会话最多四个月份，通过明确选择切换。当前余额、授权状态、动作状态不作为跨轮永久有效事实；引用对象时重新查询。银行服务未提供数据修订号时，不伪造版本：快照记录查询时间、内容哈希，用户要求“最新”时重查。查询失败和错误响应不存成事实。

上下文七天未活动后过期，读取返回明确失效状态，不静默使用旧候选。恢复仍需要可信会话身份和归属校验；当前仅合成身份，不宣称具备生产登录。display_history_json只保存最新四轮显示记录及必要业务状态；过期后清空显示历史、槽值、提案、证据快照及轮次response_json/tool_intents_json，保留归属、请求哈希、状态和原动作关联的审计记录。轮次bank_references_json只保留服务器绑定的银行对象种类、ID及toolCallId，独立于可清理的参数/响应，不包含账户金额或模型文本。过期请求ID不能重放模型，返回410并要求建立新会话；已执行资金审计按已有规则保留。

## 接口与执行顺序

1. 保持 POST `/api/chat` 原字段兼容，增可选 conversationId、requestId、expectedContextVersion。网页首次建立 conversationId 并在当前标签页 sessionStorage 保存，发送时携带请求ID与版本；首次没有会话ID由服务器创建，兼容旧客户端。
2. GET `/api/conversations/{id}` 读取归属内上下文VO：主题、选中对象、缺失参数、提案、当前动作/任务引用和版本；不返回原始凭据或模型指令。读取不会执行业务。
3. POST `/api/conversations/{id}/context/reset` 使用 expectedContextVersion，清除活动话题和未完成草案，保留已执行动作及审计。若存在已建立银行提案，返回其状态和独立取消入口，不暗中撤销或断言已停止。
4. 响应保留原 text/actions/results/answerSource/modelUsage，增 conversationId、contextVersion、context 和可空 clarification。clarification 包含业务问题、缺失槽和候选，聊天正文仍自由生成。
5. 新 ContextService 使用短事务预留 turn、读上下文并释放锁；模型请求在事务外。每会话同一时刻只处理一轮，有版本冲突或另一轮处理中返回409，不跨模型调用持有数据库行锁。
6. 模型通过限定的 `propose_business_context` 工具提出 intent、槽更新/清除和缺失参数。ContextValidationService 校验白名单、类型、月份、金额、日期、对象归属、候选引用和证据；只能更新草案，不能签发授权或直接执行。
7. 模型不再仅凭自然语言“已选小王”自行覆盖银行参数：候选选择必须对应已查询结果；多个候选而未明确选择则保持未决并澄清。无参数更改也不重复生成相同预览；提案指纹与当前 action_id 关联。
8. 一轮完成后用版本条件提交槽、证据和响应。相同requestId及相同请求哈希返回原响应，不再次调用模型；哈希不同返回409。处理中重试返回状态。进程中断导致未完成轮次标为 INTERRUPTED，先读关联原动作/任务，禁止自动重放创建或提交工具。
9. 工具创建预览前先持久化该轮工具意图，再由现有 ActionService/WorkflowService 幂等适配创建并绑定结果。必须建立原预览唯一关联；没有完成此关联前，恢复只能提示人工核对，不能重建可能已存在的动作。

槽更新在模型阶段作为该轮暂存提案，完成时统一版本提交，不在一次工具调用后悄悄提前覆盖会话。银行预览创建与该轮的关联在同一短事务提交；现有服务需补内部幂等创建入口，使用服务器预分配标识，不允许模型指定action_id。银行已创建而轮次响应尚未完成时，恢复读取原关联。槽BANK_CONFIRMED来源必须有同会话证据ID；USER_EXPLICIT需指向本轮客户原文可核对的选择，模型提出但无法核对的值仍是MODEL_PROPOSED。

## 澄清、修改和证据承接

- 账单：“看九月”明确月份→“最大那笔”复用已选月份，调用事实目录的排名，不按模型心算挑选→“和八月比”仅补查八月；“这笔合理吗”说明记录能证明什么并询问报价/用途，不把金额异常等同欺诈。
- 转账：“给小王转点钱”查候选，先消歧，再只询问必要金额/账户；缺失金额不能从余额或历史金额推断。唯一账户可展示候选建议，仍须用户核对最终卡片。
- “改成300”：更新提案金额为30000分。如果原动作尚未提交，通过原服务取消旧提案并生成新版本，旧授权不能继承；只在用户明确继续预览时创建新卡。“先别转”暂停/取消未提交提案，不执行资金操作。已受理或UNKNOWN保留原动作，先查单并阻断改参。
- “视频保留”：更新排除集合和选择集合，已完成撤销无法通过改口恢复，必须说明实际状态。没有使用记录时不自动决定哪些订阅不常用。
- 代扣确认完成：服务器根据归属内QUERY_MANDATES原动作读取已核验查询回执，记录 queriedAt、结果哈希及动作引用，使助手可解释本次查询结果。记录不是重新查询许可；换范围或要求最新状态时仍走新确认。前端只发送动作ID提示，回执内容由服务器取得。
- 储蓄：明确月付金额只能作为预算建议；现有联合任务按已核验撤销金额计算。未完成撤销时说明依赖未满足，不能把预计节省当余额或已到账金额；缺少日期则澄清。

## 回答与工具选择

Intent枚举：STATEMENT_ANALYSIS、TRANSACTION_CHECK、MONTH_COMPARISON、TRANSFER_DRAFT、MANDATE_QUERY、MANDATE_REVOKE_DRAFT、SAVINGS_WORKFLOW、ACTION_STATUS、CLARIFICATION、GENERAL。它们决定相关上下文和工具组，不决定固定话术。意图不确定时可使用只读发现工具或澄清，不能因路由漏工具就编造回答。

MODEL_GROUNDED 继续自由组织结论和证据，金额/对象必须核验。SAFE_FALLBACK 依据本轮意图及选中对象提供相关的确定性证据说明，明确核验失败；避免每次输出整份账单摘要。没有事实时询问缺少参数，不输出虚构具体内容。服务用途、退款关联和合同状态的未知边界保留。

模型只查询、计算、更新草案、生成预览；服务器授权、强验证、日累计、银行执行和UNKNOWN查原动作机制保持。候选文本、商户名和槽文本都是不可信数据，不放入高优先级系统指令。

## 调试预算和有限验收

真实 DeepSeek 联调最多4组：账单追问/跨月、重名转账/改口、代扣确认/选择、联合储蓄/暂停。先用模型协议模拟及真实本地业务服务验证，再选择本地无法证明的回答质量做真实调用；不要求4组全部跑完。

本轮真实API请求硬上限20：每次发送前集中原子预留额度，生成、审核、失败请求和修正全部计数；记录到忽略的本机调试账本，跨测试进程重启也不归零。每轮max≤5且不得超过剩余额度，余量不足以完成必要审核则停止。并发也不能突破20。单纯把聊天轮次当API请求数不可接受。

不自动重试供应商超时或扣费失败；语义修正最多一次，达到预算停止并记录未完成项。保持供应商max_tokens=2048，不为省费截断已核验答案；只发送相关上下文，报告实际token数和缓存命中。供应商未报告usage时记未知，不推算成0或声称精确费用；20次请求是次数上限，不是金额上限。

只用独立合成候选库/端口，不调用8096进行资金调试，不影响团队试用；密钥只从已授权本机文件载入子进程环境，不进入源码、命令行、报告或聊天。预算不包含团队自行使用8096产生的调用，报告分别说明范围。

验收终点：本地覆盖多轮记忆超过四轮、只问缺参、重名消歧、改参后旧授权失效、部分取消、QUERY_MANDATES确认回执承接、同请求重放、归属/版本冲突、进程中断、证据过期、提示注入和总预算；完成一次全套构建。真实调试报告保存输入、答案、可核验期望、请求数/耗时/usage，失败只做对应修复和定向复测。无新缺陷不循环扩大验收。

## 分层和交付

ConversationController → ContextService / ContextValidationService / ContextEvidenceService / ClarificationService → Context Mapper XML；Entity、请求DTO、响应VO各自独立。AgentService 保留模型协调，抽出上下文构建和意图工具选择，禁止直接访问Mapper或执行银行写操作。所有查询和修改含服务器userId。

设计审核后编写实施计划，先四表与约束，再持久化服务、上下文工具与澄清、原动作/查询回执承接、前端版本和恢复、有限真实调试。实现前建立新隔离工作区；无需替换运行中的v0.5。交付材料明确本阶段完成项、预算用量与下一阶段DAG范围，不把设计说成实现。

设计自查：已核对归属外键、版本/重放、模型事务边界、数据保留、旧grant失效与查询确认。四表DDL在独立H2内存库通过一次语法/建表校验；这不代表Mapper、并发、业务记忆或真实DeepSeek联调已通过。本设计阶段真实API请求0次。
