# SafeBank v0.2 Implementation Plan：可恢复的跨场景银行任务

> **For agentic workers:** 使用 superpowers:executing-plans 在当前会话逐项实施；需求、接口与测试采用 domain-modeling、codebase-design 和 tdd 的原则。完成阶段后执行独立代码审查。复选框仅在取得实现与验证证据后更新。

**Goal:** 在现有 v0.1 上实现“分析账单→用户选择代扣→逐项撤销→计算预计节省→授权定时储蓄”的可恢复任务，并证明超时、重复请求和部分失败不会导致错误资金动作。

**Architecture:** 保留 Java 单后端、H2 和轻量页面。抽出模型客户端与银行适配接口；用持久化 WorkflowService 管理步骤、依赖和版本，由 ActionExecutionService 统一处理提交与查单。模型负责提出目标和候选计划，服务端负责合法性、授权与状态。

**Tech Stack:** 延续 Java 21、Spring Boot 3.5.6、JDBC/H2、JUnit、原生 HTML/JavaScript；本阶段不增加 Python 服务、微服务或多 Agent 编排。

**Spec:** 项目父目录 `规划1.0.md`，以及本计划中的业务契约和验收场景。

**文档日期：** 2026-10-07（北京时间）。  
**文档状态：** 已获用户授权并执行；任务状态与验证结果见 docs/任务索引.md 和 docs/开发进度.md。
**计划窗口：** 优先争取 10/7—10/14 形成 v0.2；不是工期承诺，需结合实际可投入时间调整。  
**保留目标：** 参赛总规划中的 10/27 提交候选、11/2 截止不变。

## 二、业务契约：先统一含义

| 概念 | 固定含义 |
|---|---|
| 任务 Workflow | 用户目标及其多个依赖步骤；不等于一笔交易 |
| 动作 Action | 单个明确参数的银行写操作，有独立授权和回执 |
| 代扣撤销 | 银行侧授权终止；商户合同状态和退款状态独立 |
| 预计节省 | 根据已核验撤销且扣费周期明确的项目计算的未来估计，不增加当前余额 |
| 授权 | 用户对具体动作参数的同意；不是身份认证，也不允许任意下游动作 |
| UNKNOWN | 无法确认银行是否执行，必须查单，不得据此重新创建写动作 |
| 部分成功 | 至少一个步骤成功，其他步骤失败或未完成；逐项返回，不能称全部成功 |
| 任务版本 | 会影响业务动作的目标、约束或依赖结果发生变化后更新的版本 |

主演示使用明确为每月扣费的合成音乐 15 元、视频 68 元。缺少扣费周期或使用数据时不得补猜。用户可明确选择音乐与视频；模型可以提出候选，但不能自行认定“没有使用”或代替确认。

### 正常路径

查询账单与授权→生成任务→预览音乐撤销→用户授权并执行→预览视频撤销→用户授权并执行→程序计算预计每月节省 83 元→生成定时储蓄预览→用户授权→核验定时任务登记成功。

### 必须保留的失败路径

- 音乐成功、视频明确失败：预计节省仅 15 元；显示部分成功，新的 15 元储蓄方案需用户确认。
- 视频状态未知：不将其计入已确认节省，不生成依赖于其成功的资金动作；先查询该动作。
- 用户把收款对象或金额改掉：生成新版本，取消尚未提交的旧预览；已提交动作不通过改版本“撤销”。
- 用户刷新或服务重启：根据持久化任务找到原 action_id，不能再创建同一任务步骤的银行动作。
- 用户取消任务：阻止后续步骤；已经完成的撤销/转账仍如实保留，不自动恢复代扣或反向转账。
- 超时发生在扣款后：应用可能观察到 UNKNOWN，而银行已成功；查单核实后使用原回执。

## 三、接口与持久化设计

以下名称为实施契约；若实施时发现更合理的形状，应先更新相关任务的接口与测试，避免各模块各自改名。

### 银行与执行接口

```java
interface BankAdapter {
    BankObservation submit(String userId, String actionId);
    BankObservation lookup(String userId, String actionId);
}
record BankObservation(String actionId, BankState state,
                       String receiptId, String errorCode, Instant observedAt) {}
enum BankState { PENDING, UNKNOWN, VERIFIED_SUCCESS, VERIFIED_FAILED }
```

`LocalBankAdapter` 调用现有已授权 BankService.submit/status，保留银行侧余额、授权和幂等控制。银行适配接口处理已提交/执行的观测；尚未授权的草稿仍由应用动作记录提供，不能把AWAITING_AUTH强行映射为银行PENDING。`FaultInjectingBankAdapter` 包装本地适配器，故障只在显式测试/本地实验配置下启用。

```java
ExecutionReceipt ActionExecutionService.submit(String userId, String actionId);
ExecutionReceipt ActionExecutionService.observe(String userId, String actionId);
```

`ExecutionReceipt` 包含原动作字段、应用观察状态和银行证据。应用的观察状态单独存储，不能因为响应丢失就覆盖银行内部已成功的账务记录。兼容现有 `/api/actions/{id}` 顶层字段，但未知状态必须明确显示。

### 任务接口

```java
WorkflowView WorkflowService.create(String userId, WorkflowRequest request);
WorkflowView WorkflowService.get(String userId, UUID workflowId);
WorkflowView WorkflowService.resume(String userId, UUID workflowId, long expectedVersion);
WorkflowView WorkflowService.revise(String userId, UUID workflowId,
                                    long expectedVersion, WorkflowRequest request);
WorkflowView WorkflowService.cancel(String userId, UUID workflowId, long expectedVersion);
```

`WorkflowRequest` 记录查询月份、用户选择的 mandateIds、来源与目标账户、首次/结束日期、每月执行日，以及“仅按成功撤销项计算节省”的约束。金额由确定性逻辑推导；自由金额或不同财务目标属于新的明确请求。

`WorkflowView` 返回 id、version、状态、目标摘要、每步状态与 action_id、待确认动作、已核验结果和错误。用户身份始终来自服务端会话，不能由请求体或模型指定。

### 新增存储

- `workflows`：id、user_id、version、request_json、state、created_at、updated_at。
- `workflow_steps`：workflow_id、step_key、kind、state、action_id、input_version、evidence_json；唯一约束 `(workflow_id, step_key, input_version)`。
- `execution_observations`：action_id、user_id、state、receipt_id、error_code、observed_at。

任务步骤建立与动作预览写入使用同一应用事务，避免“动作已创建但任务关联未保存”的崩溃窗口。执行银行动作前先提交步骤与 action_id 的关联，执行期间不持有跨模型/网络请求的长数据库事务。恢复时先观察关联动作，不重复生成。

### 模型接口

```java
interface ModelClient {
    ModelReply complete(ModelRequest request);
}
```

请求/响应类型包含消息、工具定义、工具调用和用量信息。DeepSeekModelClient 与脚本化测试客户端共用这一接口；工具白名单、授权与成功回执仍由程序实施。

模型返回的结构化任务请求经过字段、归属、日期和业务约束校验。模型不是唯一计划来源：表单与测试可创建同一任务。可根据工具结果调整候选计划，但不能自行更新用户授权。

## 实施形状与决议（2026-10-07）

- 用户授权在独立项目当前开发分支实施，不额外创建工作树。T1—T5的接口与事务边界作为同一垂直切片提交，T6另行提交。

- HTTP版本字段统一为version，服务方法参数为expectedVersion；改参请求同时携带request。
- 银行明确查明NOT_SUBMITTED后，恢复原动作供用户显式重试；查询不可用不能触发此行为。
- 新增CANCEL_REQUESTED：停止后续规划，保留原已受理/未知动作并继续查单；终态核实后CANCELLED。
